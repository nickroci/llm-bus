# Coordination blocker reporting and stall detection — revision stalls-v1

## Outcome and scope

Workers report blockers when they arise. Coordinators receive a durable fallback notice when an accepted assignment or review has no recorded task communication for the configured interval. This plan serves implementers and reviewers; implementation requires separate owner approval.

- **R1:** A worker sends its coordinator a same-step blocker report whenever it records `BLOCKED` or needs a coordinator or owner decision in a task artifact. It also sends concise phase-change status and immediately reports an observed native subagent death or disconnection. Native subagents report only to their parent; their main parent handles bus communication.
- **R2:** An active local coordinator gets an informational stall notice for open `assign` and `review` directions after a configurable interval, defaulting to 30 minutes. Detection uses existing detached timer, durable mailbox and wake mechanisms. It requires no polling agent or new service.
- **R3:** Detection preserves current project generation, enrollment, grants, cancellation, decentralized machine policy and report isolation. A notice never approves, retries, cancels, reassigns or resumes work.
- **A1 (R1; T1):** Worker, coordinator and compact guidance consistently require same-step blocker communication, phase-change status and immediate observed native-child failure reporting. Examples distinguish the silent fixed-code `report` from the ordinary linked message. Existing guidance selection, version and hook-size checks pass.
- **A2 (R2; T2–T4):** With an injected clock, an eligible direction is absent before its deadline and appears at the deadline. Its communication epoch creates at most one durable notice, including concurrent timer/hook calls. Real communication rearms detection; presence and repeated identical snapshots do not.
- **A3 (R3; T2–T4):** Terminal reports, acknowledged cancellation, generation replacement, revoke, ended coordinator enrollment and denied local access prevent future notices. Histories remain intact. Remote reports and monitor data never become prompt text through detection.
- **A4 (R2–R3; T3–T5):** `llm-bus --format agent coordination stalls PROJECT --threshold 30m` returns a deterministic read-only snapshot. It does not acknowledge, record progress, apply decision defaults, spawn timers, fetch remote state or create notices. Restart recovery, unsupported wakes and unavailable remote observations are documented and tested at existing seams.

Out of scope: host stream instrumentation, inference of private task-file contents, native-child bus identities, stop-hook enforcement, automated remedial actions, deployment, installation, active-session restarts and a new scheduler service. The bus cannot independently observe a native child failure or prove task progress; R1 is an agent protocol obligation.

## Approach and material contracts

Keep immediate communication in role guidance. Add a small `coordination/stalls.py` domain module for silence projection, durable notice deduplication and deadline reconciliation. Reuse mailbox writes, authenticated reply links, report validation, lifecycle checks and detached timer launch/delivery. Do not change the existing silent `report` command or report wire schema.

### C1: Worker communication

When a worker writes a blocker or requests a decision, it records the appropriate existing fixed-code report and sends one ordinary linked message before yielding or moving to another task. The message names the task, exact worker identity/session, blocker, needed decision/action and evidence reference. The phase-change message identifies the new phase and outcome or next dependency; it is not a periodic heartbeat. The parent immediately relays an observed native child's failure, affected task and recovery choice to the coordinator. It preserves native permission boundaries and never claims a relayed answer supplies approval. If sending fails, preserve the blocker and delivery failure in existing task memory; retry only through existing recovery rules. A saved artifact alone does not satisfy this contract.

### C2: Eligible directions and silence

An eligible direction is an acknowledged `assign` or `review` sent by the current enrolled coordinator, in the current project generation, with a nonterminal work report and no later acknowledged cancel under its exact grant/sender/recipient tuple. Missing reports remain eligible. Unacknowledged sends are excluded, matching the existing meaning of open work; they remain inspectable through `direction-list`. `reprioritize`, `clarify`, gate approvals and imported directions on a worker machine are excluded.

Use an uncapped projection for detection. Preserve the existing newest-first, 100-item `direction-list` contract and its cancellation behavior. Share the underlying lifecycle predicate/row traversal rather than copy its rules. Recheck local grant validity, enrollment, session consent and scope without invoking mutating idle-expiry helpers from the read-only command. For remote recipients, validate the sender's current generation/enrollment and exact current target/grant reference, plus applicable local peer capabilities. Do not pretend a sender's target proves remote receiver consent. Remote revocations unknown locally remain an observation limitation.

A direction's silence baseline starts at acknowledgment. Subsequent evidence advances its **communication epoch** only for (a) an accepted change of report revision/status/reason, or (b) an admitted ordinary worker reply bound to that direction or its reply descendants, with the exact participants and scopes. Replies are task communication, not proof of progress or completion. Guidance requires phase messages to use that link. Unlinked messages cannot reliably identify a task and do not reset it. Coordinator messages, its notices, roster registration/`last_seen`, hooks, inbox reads, repeated identical reports and transport polling never advance the epoch.

Persist the local acceptance timestamp for new remote report revisions and admitted remote replies; never age them using an asserted remote clock. Existing fixed-code validation and machine-policy checks run first. Identical snapshots or rejected/stale revisions cannot refresh a baseline. Remote fetches remain the existing bridge's responsibility. When reports are unavailable, retain the last locally admitted observation and expose that limitation; silence does not diagnose failure.

### C3: Local durable state and public inspection

Add additive schema-16 tables, leaving existing table layouts and wire payloads intact:

- `coordination_stall_settings`: key `(scope, project_id, generation)`, storing `threshold_seconds`; absence means 1800 seconds.
- `coordination_stall_state`: key `message_id`, storing the project/generation binding, current evidence identity, `last_communication_at`, incrementing `epoch`, and `notified_epoch`/`notice_message_id`. Store identifiers and times, never report or message bodies.
- `coordination_stall_timers`: key `(scope, project_id, generation)`, storing the timer ownership token and lease expiry. This bounds timer duplication across hooks and concurrent commands; it is local bookkeeping, not distributed authority.

Exact private helper signatures and evidence encoding belong to the implementer. Event consumers update C3 in the same transaction as admitted evidence, without creating notices or wakes. Hook reconciliation repairs missing derived rows from retained source records. Existing remote snapshots/replies without a trustworthy local observation time get an explicit recovery baseline of reconciliation time, preventing fabricated historical precision. Known local acknowledgment/report times can retain their actual age. Read-only inspection never seeds missing state; it marks an unknown baseline as `observation_pending`.

Add these CLI contracts:

- `coordination stalls PROJECT [--threshold DURATION]`: coordinator-only inspection. The optional positive duration overrides this read only; accept integer `m` and `h` units, from one minute through 24 hours. Return `{project_id, generation, threshold_seconds, observed_at, items}`. Sort items by `due_at`, then `message_id`. Each stale item contains `message_id`, `recipient`, `operation`, `last_communication_at`, `due_at`, `silence_seconds`, `work_status`, `epoch`, `notified`, and `observation` (`local`, `remote_observed`, or `observation_pending`). Include pending-observation items with null age/deadline, clearly separate from known-stale entries via `observation`; they must never be claimed stale.
- `coordination stall-config PROJECT --threshold DURATION`: only the current enrolled local coordinator may change the local interval. Return the same project binding and effective `threshold_seconds`. The setting does not delegate a capability or alter grants. It persists across coordinator process restarts, resets to default for a replacement generation, and never synchronizes to peers. Omission of this new command changes no existing setup/amend semantics.

The inspection action bypasses `coordination.cli.run`'s unconditional `BEGIN IMMEDIATE` and lazy decision application. Runtime schema initialization remains the normal CLI prerequisite; the inspection action itself has no write or network side effects.

### C4: Notice, deduplication and lifecycle

Under `BEGIN IMMEDIATE`, re-read current eligibility, evidence epoch and interval. A due epoch whose `notified_epoch` differs gets one ordinary local mailbox notice addressed to the exact current coordinator. Persist notice and marker atomically. Dispatch the existing supported wake only after commit, using `locks.notices.deliver`. The notice names project, direction ID, recipient, last communication, interval and inspection command. It states that silence is informational and requires current authority/evidence checks. It does not include remote report payloads, arbitrary worker text, task artifact text or monitor content. Use the existing local informational self-notice pattern; do not impersonate the worker.

Acknowledging a notice does not rearm it. A later C2 event increments the epoch and starts a fresh interval, even if the prior notice remains unread. An interval change recomputes deadlines but does not erase the notified marker for the same epoch. There are no repeated reminders for unchanged silence. A new assignment has a separate identity. Replacement, revoke, expiry, leave, cancellation and completion stop eligibility before persistence; retained obsolete bookkeeping cannot revive an old generation or grant.

### C5: Timer and recovery

Use the existing hidden CLI timer/detach/spawn mechanism, keyed by scope/project/generation rather than current working directory. A claimed local timer sleeps toward the nearest unnotified deadline and rechecks its token, current state and lease at intervals no longer than the existing `TIMER_POLL_SECONDS`. It never calls an LLM, reads task files or polls the network. Renew its lease transactionally; the lease must outlast a poll plus a bounded scheduling margin. Losing the token ends that timer. With no eligible unnotified work, end the timer and release its own claim.

After relevant evidence commits, arrange/rearm the project timer. An event or interval reduction that moves the next deadline earlier replaces the timer token and starts the earlier timer; the superseded process exits on its next bounded check. Other callers reuse a live claim. The startup path must not leave an unexpired claim after a confirmed launch failure. Abrupt process loss is repaired after lease expiry on the next existing coordinator hook, recovery/coordinate command or relevant evidence event. Reconciliation applies already-due notices and schedules remaining deadlines. Duplicate recovery processes are safe under C4.

An awake helper attempts notice persistence at the deadline, subject to OS scheduling and database availability. Machine sleep, process loss or unavailable hooks cannot guarantee wall-clock delivery; recovery delivers overdue notices once a normal entry point runs. A failed or unsupported host wake leaves the notice durable for manual resume. No agent busy-polls. Existing launch code suppresses startup errors, so T4 must make the stall launch outcome observable without changing established lock/decision behavior.

## Decisions and discretion

The owner authorized planning both fixes, not implementation. The parent controller owns approval, independent design/simplicity review, FLOW and execution tracking. Parallel execution permission is **not requested**; execute tasks sequentially in an isolated worktree after approval. Do not alter this main checkout's source.

The default interval, inspection syntax and immediate communication scope implement the requested outcomes. The dedicated local setting command avoids modifying delegation replacement rules. No optional stop hook is planned: task artifacts and native stream events are not reliably visible to current hooks, and blocking return could prevent reporting/recovery. Routine module factoring, indexes, injectable-clock helpers and lease margins remain implementer choices within C1–C5. Material changes to eligibility, reset semantics, remote trust or notice authority return to plan approval.

## Migration and rollback

Introduce schema-16 storage before event writers, CLI consumers and timers. Do not write derived state or launch timers during schema migration. The next normal coordinator reconciliation seeds active directions and applies C3's recovery baseline. Existing messages, work reports, grants and generation history retain their meanings. No relay protocol upgrade is needed; old peers contribute only evidence already admitted through supported transport/report capabilities.

Rollback stops invoking the new scheduling/reconciliation paths and lets token/eligibility checks end owned helpers. Preserve the additive tables and notice history. Existing schema validation rejects a database newer than its supported version; do not claim an old binary can open schema 16. No supported operational downgrade procedure was established during this investigation. An older binary therefore requires restoring a pre-upgrade backup with explicit owner approval; never silently lower `user_version` or delete state. This task does not operate on the user's live database or installed skills.
