# Maintenance-aware llm-bus upgrade — revision 1

## Outcome and scope

Machine owners can pause their installed bus, upgrade or reinstall the CLI, hooks, and copied skill, verify the result, and restore service. Existing agent-facing executable paths return the approved retry instruction during the pause. Codex and Claude can remain open when their bus access is covered by the pause and all other mailbox access has stopped.

This plan targets macOS and Linux. It implements a local hold that can span the separately controlled relay retention cutover. It does not implement fleet orchestration, relay deployment, remote permission management, a schema downgrade, or a security boundary against arbitrary programs running as the mailbox owner. Implementation, production operations, backup restoration, and first deletion remain separately authorized actions.

- R1: During a completed local hold, every supported installed agent-facing entrypoint emits exactly: “llm-bus is temporarily offline for maintenance. Retry in 1 minute, then every minute while this message appears. Stop retrying once the command responds normally.” It must not open a mailbox or expose ordinary hook guidance, pending counts, or message content.
- R2: Bootstrap the hold while the installed client is still old and has no maintenance support. Cover the actual executable paths used by running hosts, not only a new PATH entry.
- R3: Stop and drain mailbox access, prevent automatic restarts, and retain a local hold across an operator-controlled relay/schema cutover. An executable gate alone never establishes that raw Python, SQLite, or already-running processes have stopped.
- R4: Upgrade and reinstall restore a verified CLI, hook integration, and the configured real skill copy from one accepted artifact identity. Preserve extras, custom host homes, unrelated settings, credentials, and local peer permissions.
- R5: Installation failure, controller death, partial alias replacement, verification failure, or reboot must not silently reopen service. Recover through the same supported local operation.
- R6: Preserve compatible rollback artifacts until release. Never reconnect an old client to an activated incompatible mailbox or restore a mailbox automatically.
- R7: Keep the change bounded and compatible with supported uv tooling: use ordinary valid uv receipts, document the managed layout, and provide working upgrade, reinstall, status, and uninstall paths.

Acceptance requires these observable outcomes:

- A1 (R1–R2; T1, T2): A disposable legacy install, including absolute cached hook paths, PATH-selected paths, and supported executable aliases, returns the exact message during hold. A hostile command argument and both output formats cannot bypass the gate. No mailbox is created or changed and no normal hook payload appears. Test both hook kinds through a minimal PATH and paths containing spaces.
- A2 (R3; T2): With a legacy bridge, detached lock timer, collaboration delivery process, and a deliberate raw Python writer, hold completion fails until access and restart sources are stopped. A test with Codex/Claude stand-ins left running succeeds after their bus entrypoints are gated. Process exit and database-handle evidence is distinct from executable-gate evidence.
- A3 (R4, R7; T3): Real disposable uv installs on macOS and Linux retain the approved response during candidate installation, verify the wheel digest and receipt, reinstall the same generation deliberately, restore hooks and skill, and resume normally. The documented generation-specific uv inspection and removal commands work. Supported aliases never expose a partially installed candidate.
- A4 (R5; T2, T3): Fault injection at each persistent state transition and filesystem switch, plus concurrent maintenance controllers, leaves a recoverable hold or a fully verified active generation. Resume after controller death cannot use a PID, elapsed time, or missing process as permission to reopen.
- A5 (R6; T3): In disposable schema-18 and schema-21 mailboxes, rollback before activation restores a compatible previous artifact. After activation, a schema-18-only previous client remains blocked, including through aliases and recovery. Retention previews, integrity, foreign-key checks, and replay/high-water preservation remain the cutover's evidence requirements.
- A6 (R1–R7; T4): A fresh operator can follow the documented legacy bootstrap, ordinary upgrade, same-version reinstall, extended hold, failure recovery, and uninstall without shutting down a whole agent host by default. Unsupported layouts fail explicitly before mailbox mutation. Repository checks pass on the final implementation.

## Approach and material contracts

Use one small standalone launcher and local maintenance controller outside the uv environment that an upgrade replaces. Reuse wheel building, receipt parsing, extras preservation, guarded host settings, and skill extraction. Do not add a bus daemon, distributed lock, central host registry, or automatic deployment controller.

The proposed managed layout uses generation-private `UV_TOOL_DIR` and `UV_TOOL_BIN_DIR` values. Each generation is installed by uv into its final location; never rename an installed virtual environment because its executable shebangs can contain absolute paths. Public entrypoints invoke the stable launcher, which selects the verified generation. This costs an explicit managed layout and generation-aware tooling, but prevents `uv tool install --force` from overwriting the live hold launcher. Redirecting only PATH or assuming uv replacement is atomic does not meet R1–R2.

- C1 — Operator interface: retain `llm-bus upgrade [--skills-dir DIR]`; add `llm-bus reinstall [--skills-dir DIR]` and `llm-bus maintenance begin|status|resume|recover`. These maintenance operations execute outside normal CLI mailbox dispatch. `begin` establishes the local hold; `upgrade` and `reinstall` enter it if necessary. An operation entered while held remains held. An operation that entered from active service may resume only after C5 passes. `status` is body-free and never opens the mailbox writable. `recover` diagnoses or completes the recorded operation and preserves the hold until explicit verified resume. Unsupported arguments fail without changing state.
- C2 — Legacy bootstrap: ship a standalone, standard-library bootstrap in `tools/maintenance_upgrade.py`, executable from an accepted checkout using an explicitly selected Python 3.12 interpreter. It must not import the installed `llm_bus` package before gating. Its `begin` operation installs the stable runtime, records recoverable originals, and atomically replaces each supported public executable alias with a launcher. It subsequently exposes C1 even when the old CLI cannot parse maintenance commands. Normal installation establishes this runtime for later operations. No network-fetched bootstrap, package-source patching, or reliance on an old process reading a new marker is allowed.
- C3 — Entrypoint and mailbox boundaries: inventory uv receipt entrypoints, PATH matches, hook command paths in effective and remembered host homes, and owner-declared service/client paths. Resolve symlinks and distinguish their aliases from hardlinks or copied scripts. Replace each supported path itself without following an unowned symlink destination; retain the pre-change bytes, mode, link target, and expected identity. Unknown, unwritable, ambiguous, hardlinked, or unregistered copied executable layouts block hold completion until explicitly retargeted or excluded by stopping their callers. Cached old hook paths continue to route through the launcher after release. Existing direct interpreter invocations, `python -m llm_bus`, imported `Store`, raw `sqlite3`, viewers, and open processes are separately inventoried access paths; stopping or retargeting those callers is required. New installed `llm_bus:main` and `python -m llm_bus` entrypoints check maintenance before eager application imports or mailbox dispatch, but this does not retrofit old interpreters or guard raw DB access.
- C4 — Local state and admission: use one owner-only runtime directory under `~/.local/share/llm-bus/` and one owner-only operation journal under `~/.local/state/llm-bus/`. Record the operation identity, phase, exact mailbox identities, original aliases, generations and receipts, wheel digests, integration snapshots, restart-source state, and verification results. A local OS lock serializes controllers; it is not an llm-bus mailbox lock. Durable intent precedes each mutation, followed by an atomic state update with file and parent-directory durability. Missing, malformed, partially committed, or inconsistent managed state fails closed. The hold has no automatic expiry. Distinguish `preparing`, `held`, `verified`, and `active`; `preparing` is never proof of quiescence. New launcher admissions and transition to hold share a race-free local protocol; track/drain admitted children for their full bus lifetime, including detached descendants. Legacy processes require the separate C3 inventory and drain.
- C5 — Release barrier: restore ordinary dispatch only after alias coverage, stopped-access evidence, candidate identity and compatibility, CLI/module checks, hooks, and skill verification succeed for the recorded mailbox set. For a schema-changing release, remain held until the owner's separately authorized cutover supplies the exact compatible floor, local schema verification, stopped relay-side drain evidence, and first-deletion approval required by `docs/remote-bus.md:Offline retention cutover`. Local code must not infer these from a relay response, another agent's message, or successful installation. The accepted candidate may perform narrowly scoped owner-invoked preview/migration/verification while held through the controller's private execution path; ordinary agents have no command or environment-variable bypass. A help-only smoke test is never migration or compatibility proof.
- C6 — Process control: stop identified bus processes and suspend their known restart sources through existing owner-controlled host/service mechanisms. Record exact process identities and actions; never kill a process by a substring match or stop a whole host merely because it contains a bus-using session. Provide an explicit operator-assisted stop/drain path for unsupported supervisors. Verify all known mailbox files, including WAL/shared-memory companions and `LLM_BUS_DB` overrides, have no unexplained accessors; use available platform process/handle inspection. A one-time empty handle list cannot prove a dormant raw Python client will not reopen later. Its caller and restart source must also be controlled. Missing inspection capability or unknown access blocks the release barrier. No automatic arbitrary shell-command framework is needed.
- C7 — Installation and recovery: install candidates into immutable final generation paths, retaining valid uv-generated receipts. Verify receipt wheel/extras/interpreter and distribution provenance against the accepted artifact; invoke the candidate by exact path with a minimal PATH and separate disposable mailbox where needed. Publish its active reference atomically only after verification. Preserve the existing previous wheel, integration snapshots, and compatible generation until the operation is released. Before rollback, inspect mailbox compatibility read-only and validate the recorded floor; unknown compatibility keeps the hold. Never run an old binary against the real mailbox to discover whether it supports it. After schema activation, recover using a verified compatible generation. Backup restoration and replay/high-water reconciliation remain offline, owner-authorized procedures.
- C8 — Integration and tooling: a managed installation records the real skill destination; bootstrap must require it explicitly if discovery is ambiguous. Reinstall and subsequent upgrade restore that copy from the same accepted source revision, refusing symlink destinations as today. An explicit `--skills-dir` overrides the recorded real destination. Use the existing guarded settings merge/restore behavior for effective host homes and preserve unrelated concurrent changes. Verify already-running hosts use captured gated paths; do not assume they reload rewritten settings. Document that default `uv tool list` no longer identifies the selected generation; provide exact recorded `UV_TOOL_DIR`/`UV_TOOL_BIN_DIR` inspection commands. `llm-bus uninstall` must remove owned public launchers, aliases, integrations, and owned generation registrations while preserving mailbox/policy/history and unrelated tools. Direct uv removal of one generation must not silently select another; the launcher fails closed and points to supported recovery.

During hold, agent CLI invocations print R1's approved message to stdout, with a trailing newline, and exit 75. Hook invocations print the same message and exit 0 so routine host hooks do not become persistent hook failures. Neither form sleeps or retries internally. Operator diagnostics use the maintenance interface and cannot append extra agent-facing text. File ownership and path validation protect accidental cross-user edits; they do not claim isolation from another program with the same owner's privileges.

The local journal may be kept held while other machine owners and the relay operator perform their cutover. Resume checks local evidence and requires the relevant external cutover acknowledgment; it does not change remote state. A machine that cannot establish the barrier remains disconnected. The existing retention sequence, backup semantics, policy enforcement, and report/monitor isolation remain authoritative.

## Decisions and discretion

Confirmed scope is planning only, continuous maintenance messaging, local extended holds, and keeping agent hosts open when safe. The stable-launcher/generation layout and C1's new commands are proposed design decisions for independent review and owner plan approval. The changed default uv discovery behavior must be visible in that approval; valid per-generation receipts do not preserve default-directory discovery.

The implementer can choose private module boundaries, journal encoding, local lock primitive, and exact platform inspection commands within C2–C8. Unsupported platforms/layouts must fail explicitly; they must not be silently treated as quiescent. A new persistent service, unsafe receipt rewriting, generation relocation, or weaker admission guarantee requires a plan revision. There is no implementation or parallel-execution approval in this document.

## Verification and rollback

Extend existing upgrade, portability, restore, and package checks at the demonstrated gaps in A1–A5. Add focused subprocess/concurrency regressions because mock uv calls and help-only tests cannot detect entrypoint gaps, legacy access, detached children, or crash recovery. Use disposable homes, generation directories, settings, mailboxes, and service stand-ins. Do not run or start actual agent hosts, bridges, supervisors, or relays for acceptance tests.

Run cheap syntax, collection, layout, and focused checks before the real-uv scenarios, then the repository-required `uv run poe check` on the final code. macOS and Linux evidence must identify Python/uv versions and the exact tested artifact. Preserve unique failure diagnostics and compatibility results in the execution report; remove task-created disposable environments and processes after verification. No persistent new CI service or separate maintenance job is required.

Recovery follows C4 and C7. Before mailbox activation, restore verified compatible artifacts and bus-owned integration changes while retaining unrelated concurrent edits. After activation, leave the hold in place until a compatible candidate is verified. Never remove the journal/marker merely to make the command work. Pruning is post-release housekeeping and cannot invalidate the active generation or the retained compatible recovery path.
